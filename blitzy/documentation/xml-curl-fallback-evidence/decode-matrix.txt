LIVE BADGERFISH DECODE MATRIX - WARNING <-> EVENT 1:1 PAIRING
============================================================

WHAT THIS IS
  The five-case live decode matrix, re-run AFTER the fallback event was added, so
  the pairing the event exists to provide is measured rather than assumed.  The
  pre-event run recorded only WARNING counts; this one records, per case, the value
  the lookup resolved, the fallback WARNINGs the log gained, the
  xml_curl::json_fallback events an ESL consumer received, and the three headers
  each event carried.

HOW TO REPRODUCE
  run-decode-matrix.py in this directory is the harness, python3 standard library
  only.  It starts its own loopback provisioning gateway, drives the instance over
  the inbound event socket, and restores the configuration it borrows - including on
  failure.  It exits non-zero unless every case matches AND every case pairs 1:1.

    python3 run-decode-matrix.py --prefix /usr/local/freeswitch

  The run archived below used a private prefix and clone-unique ports, because this
  host runs several FreeSWITCH trees side by side:

    python3 run-decode-matrix.py \
        --prefix /tmp/fs014-install \
        --conf-dir /tmp/fs014-install/etc/freeswitch \
        --log /tmp/fs014-install/var/log/freeswitch/freeswitch.log \
        --esl-port 18021 --gateway-port 18094

  The instance loaded seven modules and deliberately NOT mod_signalwire, so nothing
  in this evidence can carry an adoption token.

WHAT THE FIVE CASES ESTABLISH
------------------------------------------------------------
  1. json_happy_path              a conformant BadgerFish response decodes: the
                                  lookup resolved badgerfish-json, and neither
                                  signal fired.
  2. malformed_json               truncated bytes announced as JSON: 2 WARNINGs, 2
                                  events, Fallback-Reason=malformed-json.  The
                                  lookup then failed because the body was not XML
                                  either - a fallback, not a rescue.
  3. wrong_content_type           a conformant JSON body announced as text/xml: 2
                                  WARNINGs, 2 events,
                                  Fallback-Reason=content-type-mismatch.  The
                                  announcement is what the classifier judges.
  4. xml_default_backward_compat  response-format ABSENT: the lookup resolved
                                  classic-xml, 0 WARNINGs and 0 EVENTS.  This is
                                  the bit-identical-behaviour requirement,
                                  including the "no events fired" half of it.
  5. xml_via_json_total_fallback  an XML response to a JSON-configured binding: 1
                                  WARNING, 1 event, content-type-mismatch, and the
                                  lookup STILL RESOLVED classic-xml.  Total
                                  fallback: the degradation is signalled and the
                                  provisioning lookup survives it.

  Case 5 firing an event immediately after case 4 fired none also proves the
  consumer was still connected and subscribed during case 4, so its zero is an
  observed zero rather than a lost subscription.

  TOTAL: 5 fallback WARNINGs, 5 fallback events, 5 of 5 cases 1:1.
